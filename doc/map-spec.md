# 地図データ仕様書: OSM → NES の地形

NES(ファミコン)の ROM が、世界地図の上を歩けるようにするための、地図データの仕様。
OpenStreetMap(OSM)のベクターデータと国土地理院の標高から、z18 のマスを**事前に**作って SQLite に入れ、
NES からの要求ごとに、サーバーが SQLite から地形 ID を**動的に**作って返す。

- 実装は `server/`(Bun + TypeScript、依存パッケージなし)、ROM は `src/` と `gfx/`。
- この文書は**実装の現状**を書いた仕様書。食い違いを見つけたら、実装を正として文書を直す。
- 最終更新: 2026-11-08。関東全域(約 1.2 万ブロック)で実データのビルドと動作を確認済み。日本全国はまだ。

## 1. 概要

- 地図からマスを**その場で作らず**、OSM のベクターデータから**事前に** z18 のマスだけを作る。
- DB に入れるのは、NES の地形 ID ではなく、**OSM の種別**(属性)。ゲームの地形への変換は実行時に行う。
- z17 以下のマスと、地形 ID は、要求(z/x/y)ごとに SQLite から**動的に**作る。低ズーム用のピラミッドは持たない。
- 山・岩山の判定には、国土地理院の標高(DEM)から求めた傾斜を使う。
- パイプライン全体が Bun だけで動く(osmium・GDAL は不要)。陸と海は、OSM の海岸線から作る。

## 2. 座標とズーム

- 世界の 1 辺は 2^(z+4) マス。1 タイル(256px)= 16×16 マスで、1 マス = タイル上の 16×16px。
  座標は Web メルカトル(北が y=0)。ROM は座標を 24bit で持つ(z18 では上位 2bit が常に 0)。
- ズームは **z1〜z18**。z18 の 1 マスは約 7.8m(北緯 35°。北海道で約 6.8m、沖縄で約 8.6m)。
- **ブロック** = z18 の 256×256 マス = z14 のタイル 1 枚(約 2km 四方)= z10 の 1 マス。DB の 1 行。
  ブロック座標 `(bx, by)` は z14 のタイル座標に等しい。
- 世界の x は経度方向なので巻き戻す。y が範囲外なら岩山(極の外側)を返す。

| z | 1 マス | NES の 1 画面(16×15 マス)の横幅 |
| --- | --- | --- |
| 10 | 約 2km | 約 32km |
| 12 | 約 510m | 約 8km |
| 14 | 約 130m | 約 2km |
| 16 | 約 32m | 約 510m |
| 17 | 約 16m | 約 250m |
| 18 | 約 7.8m | 約 125m |

## 3. 全体構成

```
[事前ビルド]  server/build_world.ts  (地域ごとに実行。関東全域で約 6 分)
  OSM (Geofabrik の地方別 pbf) ─┐
  国土地理院の標高タイル (z14)  ─┼─→ z18 のマスに塗る ─→ data/world.sqlite
  (海岸線は pbf の natural=coastline) ┘   (OSM 種別 + 傾斜)

[実行時]  server/mapserver.ts  (NES とは TCP/シリアルで 9 バイトの要求・応答)
  NES ──(z, x, y, 縦/横, n)──→ answer()
                                └ OsmSource (server/osmsource.ts)
                                    ├ 代表値は起動時に全部メモリへ。data はブロック単位で LRU
                                    ├ z18 のマスを z に合わせて集約
                                    ├ OSM 種別 → 地形、線路の向きを決定
                                    └ 地形 ID (1 バイト) を返す
```

- DB がなければ、サーバーはノイズで作った仮の世界(`SyntheticSource`)を返す。
- ROM は、サーバーから応答がなければ(約 0.3 秒で打ち切り)、以後 ROM 内の簡易生成(`src/worldgen.c`)に切り替える。

## 4. 入力データと取得

`data/` はリポジトリに含めない(`.gitignore`)。取得は `bun server/download.ts`。

| 置き場所 | 内容 | 取得 |
| --- | --- | --- |
| `data/osm/<地域>-latest.osm.pbf` | OSM。Geofabrik の地方別(hokkaido / tohoku / kanto / chubu / kansai / chugoku / shikoku / kyushu)または日本全体 | `download.ts osm <地域>` |
| `data/dem/14/{x}/{y}.png` | 国土地理院の標高タイル(`dem_png` z14、DEM10B)。0 バイトのファイルは「タイルなし(海など)」 | `download.ts dem --bbox w,s,e,n` |
| `data/osm/land-polygons-split-3857/land_polygons.shp` | (任意)陸地ポリゴン。通常は使わず、pbf の海岸線から陸を作る | `download.ts land`、`build --land` |
| `data/start.json` | (任意)ROM の起動位置。緯度経度とズーム | 手で書く(14 章) |

- `download.ts all <地域> --bbox ...` は、pbf と標高をまとめて取得する。既存ファイルは取り直さない(`--force` で取り直す)。
- pbf のノードは **ID 順**に並んでいる必要がある(Geofabrik のファイルは満たす。そうでなければ `osmium sort`)。
- 標高タイルの z14 は、ブロックと同じ格子(256px = 256 マス)に揃っているので、再標本化は要らない。

## 5. データベース(`world.sqlite`)

形式は `server/worlddb.ts` が定義し、ビルダー(書き込み)・サーバー(読み取り)・テストが共有する。

```sql
-- OSM の種別(マスの属性が参照する)。id は 1 から。既存の id がずれないよう、足すときは末尾に
CREATE TABLE osm_class (
  id    INTEGER PRIMARY KEY,
  kind  INTEGER NOT NULL,      -- 0=面 1=道路 2=線路
  key   TEXT NOT NULL,         -- 'landuse' / 'highway' / 'railway' ...
  value TEXT NOT NULL,         -- 'farmland' / 'primary' / 'rail' ...
  rank  INTEGER NOT NULL       -- 面: 重なったときの勝ち順 / 道路・線路: 大きいほど幹線
);

-- z18 のマス本体。data は大きいので最後に置く (代表値だけ読むとき、オーバーフローページをたどらずに済む)
CREATE TABLE block (
  bx        INTEGER NOT NULL,  -- = z14 タイル x
  by        INTEGER NOT NULL,  -- = z14 タイル y
  -- 代表値 (z10 以下の生成用。サーバー起動時に全部メモリへ載せる)
  area      INTEGER NOT NULL,  -- 最も多い面種別 (osm_class.id)
  area_pct  INTEGER NOT NULL,  -- その割合 0〜100
  road      INTEGER NOT NULL,  -- ブロック内で最上位の道路 (0=なし)。高速道路を除く
  rail      INTEGER NOT NULL,  -- ブロック内で最上位の線路 (0=なし)
  motorway  INTEGER NOT NULL,  -- 高速道路を含むか (0/1)
  mount_pct INTEGER NOT NULL,  -- 山になるマスの割合 0〜100
  rock_pct  INTEGER NOT NULL,  -- 岩山になるマスの割合 0〜100
  data      BLOB,              -- 256×256 マス × 4 バイト を zlib 圧縮。全マス同じなら NULL
  PRIMARY KEY (bx, by)
) WITHOUT ROWID;

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);   -- zoom=18、built_at、license
```

- 行がないブロック(日本の範囲外、海だけのブロック)は**海**として扱う。
- `data` が NULL のブロックは、全マスが `(area, 0, 0, 0)`(面だけで、道路・線路・傾斜なし)。

### 5.1 1 マスの 4 バイト(`data`、行優先、1 マス 4 バイト)

| バイト | 内容 |
| --- | --- |
| byte0 | 面の種別(`osm_class.id`、kind=0) |
| byte1 | 一般道路の種別(kind=1。高速道路を除いて最上位のもの。0 = なし) |
| byte2 | 線路の種別(kind=2。0 = なし) |
| byte3 | bit0 = bridge、bit1 = cliff、bit2〜4 = 傾斜の段階(0〜7)、bit5 = 高速道路あり |

- 高速道路は byte1 に入れず bit5 で持つ。高架の高速道路の下を一般道路がくぐるマスで、一般道路の情報を失わないため。
- 道路と線路は面と別のバイトなので、建物や農地の上を通っていても両方残る。
- `tunnel=yes` の道路・線路は格納しない(地上の地形を出す)。
- bit0 の bridge は記録するが、現在のサーバーは使わない(橋の地形はない。水の上の道路は道路)。
- ビルド中だけ byte3 の bit6 を「陸地ポリゴンの内側」の作業用に使うが、書き出す前に消す。

傾斜の段階: 0=5° 未満、1=10° 未満、2=17° 未満、3=25° 未満、4=35° 未満、5=45° 未満、6=60° 未満、7=60° 以上。
山は段階 4 以上(25°)、岩山は段階 6 以上(45°)を境にする。

### 5.2 `osm_class`(`server/worlddb.ts` の `CLASSES`。43 行)

| id | kind | OSM のタグ | rank | ゲームでの扱い(`cat`) |
| --- | --- | --- | --- | --- |
| 1 | 面 | `natural=grass` | 1 | 草(何もない陸の既定) |
| 2〜4 | 面 | `landuse=meadow` / `farmland` / `orchard` | 2 | 農地 → 草と同じ |
| 5〜6 | 面 | `landuse=forest`、`natural=wood` | 3 | 森 |
| 7〜8 | 面 | `natural=beach` / `sand` | 4 | 砂 |
| 9 | 面 | `natural=glacier` | 4 | 雪 → 岩山と同じ(日本にはほぼない) |
| 10〜11 | 面 | `natural=scree` / `shingle` | 5 | 山 |
| 12 | 面 | `natural=bare_rock` | 6 | 岩山 |
| 13〜16 | 面 | `landuse=residential` / `commercial` / `retail` / `industrial` | 7 | 市街地 → 建物と同じ |
| 17 | 面 | `natural=wetland` | 8 | 湿地 |
| 18〜21 | 面 | `natural=water`、`waterway=riverbank`、`landuse=reservoir`、海(`sea=sea`) | 9 | 水 |
| 22 | 面 | `building=*`(値は区別せず 1 行) | 10 | 建物 |
| 23〜35 | 道路 | `highway=trunk` 90 / `primary` 80 / `secondary` 70 / `tertiary` 60 / `unclassified` 50 / `residential` 45 / `living_street` 40 / `service` 35 / `track` 30 / `pedestrian` 25 / `footway`・`path`・`steps` 20 | 左記 | 道路 |
| 36〜39 | 線路 | `railway=rail` 90 / `subway` 70 / `light_rail` 60 / `tram` 50 | 左記 | 線路 |
| 40〜43 | 面(駅) | `building=train_station` / `public_transport=station` / `railway=station` / `railway=platform` | 11 | 駅(9.4) |

- 面は、複数のタグがあれば rank の高いものを取る(`building=train_station` は `building=yes` より先に判定する)。
- 高速道路(`highway=motorway` / `motorway_link`、`motorroad=yes`)は byte3 の bit5。
- 別名: `*_link` は親の道路、`cycleway` / `bridleway` は `path`、`monorail` / `narrow_gauge` は `light_rail`。
- 歩道(`footway=sidewalk`)・横断歩道(`footway=crossing`、`cycleway=crossing`)は道路に入れない
  (車道の隣のマスがすべて交差点になるため)。
- 川は `waterway=river` / `canal` の線を水として塗る。`stream` は塗らない(細い沢で道がふさがれるのを防ぐ)。
- `natural=cliff` の線は byte3 の bit1(崖)。

## 6. 事前ビルド

`bun server/build_world.ts build --bbox w,s,e,n [--pbf ...] [--out ...] [--no-dem] [--tile 16] [--margin 0.05]`

### 6.1 地物の取り出し(`server/osmpbf.ts`、`server/osmfeatures.ts`)

PBF を 3 回読む。

1. リレーション: 面のタグを持つ multipolygon を集める。
2. ノードとウェイ: 範囲(+ margin)内のノードを集め、必要なウェイ(タグが該当し、範囲にかかるもの、または multipolygon のメンバー)を保持する。
   タグのあるノードのうち、`railway=station` / `halt`、鉄道の `public_transport=station` は駅の候補として集める。
3. 必要なノードの座標: 必要な ID を整列し、ID 順の PBF ノードとマージ結合で集める(ハッシュ表を持たない)。

- ウェイと参照は型付き配列に詰め、地物(`FeatureStore`)は、列ごとの型付き配列と 1/64 マスの固定小数点 Int32 の座標列に入れる
  (メモリを抑えるため)。座標はマス座標(z18、小数)。
- multipolygon は、メンバーのウェイを端点でつないでリングにする(外周と穴を区別せず、偶奇で塗る)。
- 範囲の外に頂点があるだけで範囲を覆う大きな面は取りこぼす。`--margin`(度)で外側を広げて対処する。

### 6.2 陸と海(`server/coast.ts`)

- 海岸線(`natural=coastline`)は、陸が進行方向の左になるよう向きがそろっている。ウェイを向きを変えずにつないで鎖にする。
- 鎖を対象範囲(窓)で切り、窓の枠を反時計回りにたどって次の鎖の始点につなぐと、陸の輪が閉じる。
- 地方別 pbf の境で切れて窓の中で途切れた端は、最後の線分の向きに枠までまっすぐ延ばして閉じる。
- 窓の中で閉じた輪は、向きで島(陸を囲む)か陸の中の水域(穴)かを決める。海岸線がなければ、陸の地物があれば窓全体を陸とする。
- 陸の外側(陸地ポリゴンの外)で面が何もないマスが海になる。`--land` で陸地ポリゴンの shapefile を使うこともできる。

### 6.3 マスへの塗り(`server/worldbuild.ts` の `Painter`、`server/rasterize.ts`)

範囲を 16×16 ブロックのタイルに分け、タイルごとに、余白 `PAINT_MARGIN` = 8 マスをつけた作業台に塗る。
作業台のマスは 4 バイト。塗る順は次のとおり。

1. **陸**: 陸の輪を偶奇で塗る(作業用 bit6)。
2. **面**: rank の低い順に塗る(高いものが上に来る)。マスの中心がポリゴンに入れば塗る。駅の面は塗らず、9.4 のとおり扱う。
3. **線**: rank の低い順に塗る。
   - 道路・高速道路・川・崖: 触れたマスを全部塗る(4 連結)。斜めの線も上下左右につながるので、上下左右にしか動けない NES でも歩ける。
   - **線路: 1 マスに 1 つの細い線(8 連結)**で塗る(`linePathThin`)。折れ線を細かくたどり、各列の中心線を横切るマス
     (横向きの所)と、各行の中心線を横切るマス(縦向きの所)を取る。向きは前後 1.5 マスの平均の傾きで決める。
     傾き 45° 付近(0.8〜1.25 倍)は、切り替わりで 1 マス飛ばないよう両方を取る。
4. **駅のマス**: 9.4 の位置に置く。
5. **線路の細線化**(`thinMask`、Guo–Hall 法): 並走する線路(複線)、ホームの塗りつぶし、操車場を、1 マス幅の中心線にする。
   つながりと端点は保たれ、本当の分岐点だけが残る。判定は周囲 8 マスだけで決まる。
   (Zhang–Suen 法は、幅 2 の斜めの帯を丸ごと消すので使わない。)
6. **市街地の補完**: 建物のマスから `URBAN_RADIUS` = 3 マス以内で、面が何も塗られていない陸のマスを、市街地(`landuse=residential`)にする。
   OSM は建物の隙間や庭を塗らないので、そのままだと市街地の中に草の斑点ができ、斜面で山になるため。
7. **ブロックにまとめる**: 面が何もないマスは、陸なら草(`natural=grass`)、海なら海。傾斜を byte3 に入れる。
   全マスが海で何もないブロックは行を作らない。

### 6.4 傾斜(`server/dem.ts`)

- 国土地理院の標高タイルは RGB で標高を表す: x = R×65536 + G×256 + B。x = 2^23 は無効、x < 2^23 なら x×0.01 m、それ以外は (x − 2^24)×0.01 m。
- 周囲 1 マスの余白つき(隣のタイルの端を使う)の標高から、中心差分で傾斜を求める。3857 の長さは緯度で伸びるので cos(緯度) で補正する。
- タイルがなければ 0 m として扱う(海など)。`--no-dem` なら傾斜は 0。

### 6.5 書き込みと実行

- ブロックごとに代表値(5 章)を計算し、`data` を zlib 圧縮して書く。全マスが同じなら `data` は NULL。最後に `VACUUM`。
- ブロックは途中で切らない(bbox をブロックの範囲に広げる)ので、複数回の実行で同じ DB に追記できる。
  日本全国は、地方別 pbf を順に build する(地方の境のブロックは後の実行が上書きする)。
- タイルごとに GC を呼ぶ。メモリ(関東全域): 地物の構築後 約 2〜3GB、ピーク(OS から見た値)8〜9GB。

## 7. 1 マスの地形の決め方(z18)

z18 のマスについて、上から順に判定する(`OsmSource.cell`)。

| 順 | 条件 | 地形 |
| --- | --- | --- |
| 1 | 面が駅のマス | 駅 |
| 2 | 同じマスに道路と線路の両方がある | 踏切(線路の向きで 2 種) |
| 3 | 一般道路または高速道路がある | 道路(向きなし。水の上も) |
| 4 | 線路がある | 線路(7.1) |
| 5 | 面が建物・水・湿地 | 建物・水・湿地 |
| 6 | cliff フラグ、`natural=bare_rock`、または傾斜 45° 以上 | 岩山 |
| 7 | `natural=scree` / `shingle`、または自然地(森・草原)で傾斜 25° 以上 | 山 |
| 8 | それ以外 | 面の種別に対応する地形(5.2) |

- 道路・線路を岩山・湿地より先に判定するので、岩山の上の登山道や湿原の木道は通れる(5 の水・湿地・建物は、道路・線路が通れば道路・線路になる)。
- 高速道路は道路と同じ地形にまとめたので、歩ける。陸橋で線路をまたぐ道路も、同じマスに道路と線路があるので踏切になる。
- 面と地形の対応: 市街地→建物、農地→草、雪→岩山、砂→砂、scree→山。

### 7.1 線路の向き(`server/rail.ts`)

- 線路のマスは、隣 8 方向のうち線路のあるものを見て、「通る 2 方向」で決める。方向は 0=E 1=SE 2=S 3=SW 4=W 5=NW 6=N 7=NE。
- 斜めの隣は、挟む上下左右のどちらかにも線路があれば、それを経由するので捨てる(L 字の角を斜めに近道しない)。
- 行き止まり(1 方向)は、その方向を通る直線。孤立は横。分岐・交差(3 方向以上)は、角度の差が最も大きい(まっすぐな)組み合わせ。
  鋭い折り返し(差 45°)は、片方を通る直線にする。
- 組み合わせは、角度の差が 90° 以上の **20 種**: 直線 4(横・縦・╲・╱)、45° の曲がり 8、90° の曲がり 8。
  タイル ID = `T_RAIL` + `RAIL_PAIRS`(`server/rail.ts`)での位置。ROM の絵(`gfx/gen_chr.ts`)も同じ並び。
- 踏切の向き: 線路の 2 方向のうち東西を通るなら「線路が横」、南北を通るなら「線路が縦」(斜めだけなら横)。

## 8. ズームごとのマスの作り方

ズーム z の 1 マスは、z18 の 2^(18−z) 四方のマスに当たる。すべて実行時に集約する。

| z | 1 マス = z18 の | 読むもの | 作り方 |
| --- | --- | --- | --- |
| 18 | 1×1 | `data` | 7 章の判定そのまま |
| 11〜17 | 2×2 〜 128×128(必ず 1 ブロックに収まる) | `data` | 全マスを集約(8.1) |
| 10 | 1 ブロック | 代表値 | 1 マス = 1 行(8.2) |
| 6〜9 | 2×2 〜 16×16 ブロック | 代表値 | 代表値を集約(8.2) |
| 1〜5 | 32×32 ブロック以上 | 代表値 | 16×16 ブロックだけ間引いて読む(8.2) |

- 隣のマス(線路の向き)を見るために、各マスの特徴(道路・高速・線路・踏切・地形)をキャッシュする(30 万件まで)。
- 代表値は起動時に全部メモリへ載せる(行数が 200 万以下のとき)。z6 以下で、1 マスにつき最大 256 行を読むため。

### 8.1 data からの集約(z11〜17)

1. **道路**: 子マスのどれかに道路があり、その種別が 8.3 のしきい値以上なら道路。どれかにあれば残す(OR)ので、道路のつながりは崩れない。
2. **高速道路**: byte3 の bit5 を OR。表示は z6 以上。道路と同じ地形。
3. **線路**: 道路と同じ処理。しきい値は 8.3。
4. **踏切**: 同じ子マスに道路と線路の両方がある場合だけ(並走する道路と線路を、まとめたときに踏切にしない)。
5. **岩山**: 7 章の 6 に当たる子マスの割合が 30% 以上(z17・z18 では 1 つでもあれば)。
6. **山**: 7 章の 7 に当たる子マスの割合が 40% 以上。
7. **駅**: 子マスに駅が 1 つでもあれば駅(1 つの駅に 1 マスだけなので、多数決では埋もれるため)。
8. **面**: 子マスの byte0 の多数決。同数なら rank の高い方。建物・水・湿地・駅になる面は、岩山・山より優先。

### 8.2 代表値からの集約(z10 以下)

- 道路・線路・高速道路: しきい値以上のブロックが、一辺のブロック数(最大 16)の**半分以上**あるときだけ出す
  (1 つでもあれば出すと、z8 以下で関東は全面が道路になる)。
- 岩山: `rock_pct` の平均が 30% 以上。山: `mount_pct` の平均が 40% 以上。
- 面: `area` の多数決(`area_pct` で重みづけ)。
- 行のないブロックは海(面 100%)として扱う。
- 代表値には位置の情報がないので、z10 以下では踏切と駅は出さない(道路・線路として出す)。

### 8.3 ズームごとに出す道路・線路(`ROAD_MIN` / `RAIL_MIN`)

| z | 一般道路 | 高速道路 | 線路 |
| --- | --- | --- | --- |
| 18 | すべて(`footway` / `path` / `steps` も) | 出す | すべて |
| 17 | `residential` 以上 | 出す | すべて |
| 16 | `tertiary` 以上 | 出す | すべて |
| 15 | `secondary` 以上 | 出す | すべて |
| 13〜14 | `primary` 以上 | 出す | `rail` / `subway`(rank 70 以上) |
| 12 | `trunk` | 出す | `rail` / `subway` |
| 11 | `trunk` | 出す | `rail`(rank 90 以上) |
| 6〜10 | 出さない | 出す | `rail` |
| 1〜5 | 出さない | 出さない | 出さない |

- 都心(東京駅・渋谷・豊洲)で、道路マスが画面の 20〜50% に収まるように決めた(当初の案では z12〜15 で 60〜99%)。
- z10 以下で一般道路を出さないのは、関東では `trunk` 以上が陸のブロックの約 6 割にあり、何を基準にしても全面が道路になるため。

## 9. 地形の種類と ROM

### 9.1 地形 ID(32 種)

ID は `src/terrain.h`、`server/terrain.ts`、`gfx/gen_chr.ts` の並びで一致させる(ROM のタイル番号 = ID × 4)。

| ID | 地形 | 通行 | パレット |
| --- | --- | --- | --- |
| 0 | 草(農地も) | 可 | 緑 |
| 1 | 森 | 可 | 緑 |
| 2 | 山(なだらかな丘) | 可 | 緑 |
| 3 | 岩山(高い峰と低い峰) | 不可 | 黒/濃い灰/白 |
| 4 | 水 | 不可 | 青 |
| 5 | 建物(市街地も。緑の地に、ビル 1 棟と赤い三角屋根の家 1 軒) | 不可 | 黄/赤 |
| 6 | 砂(黄色) | 可 | 黄/赤 |
| 7 | 湿地 | 不可 | 緑 |
| 8 | 道路(向きなし。高速道路・橋も) | 可 | 黒/濃い灰/白 |
| 9〜28 | 線路 20 種(7.1) | 不可(z14 以上) | 黒/濃い灰/白 |
| 29〜30 | 踏切(線路が横・縦。緑の地に灰色の道路を、白黒の線路が横切る) | 可 | 黒/濃い灰/白 |
| 31 | 駅(黒い円盤に白い電車の正面) | 可 | 黒/濃い灰/白 |

- 通行不可は、水・岩山・建物・湿地、および線路(線路は z14 以上のみ。z13 以下では低ズームで踏切や高架下を判定できず、
  地図が線路で分断されるので通す)。建物が不可なので、街中は道路沿いにしか歩けない。
  市街地として補完した「何もない陸」も建物なので通れない。
- BG のパターンテーブルは 4KB(64 種)、使用 32 種。BG パレットは 4 つ、1 マスにつき 1 パレット。

### 9.2 パレット(`src/main.c` の `palette[]` と `tile_pal[]`)

| パレット | 色(NES) | 使うもの |
| --- | --- | --- |
| 0 緑 | 濃い緑 `0A` / 薄い緑 `2A` / 茶 `17` | 草・森・山・湿地 |
| 1 黄/赤 | 黄 `28` / 淡い黄 `38` / 赤 `16` | 砂・建物 |
| 2 黒/濃い灰/白 | 黒 `0F` / 濃い灰 `00` / 白 `30` | 岩山・道路・線路・踏切・駅 |
| 3 青 | 青 `11` / 薄い青 `21` / 茶 `17` | 水 |

- 全パレットの色 0 は緑(`1A`、草の地色)。線路・駅・建物は、この緑の地に描く。
- 駅は、市街地(黄・赤)と違う黒白にして、見分けやすくした。

### 9.3 タイルの絵(`gfx/gen_chr.ts`、16×16。ROM の CHR `gfx/tiles.chr` を生成)

- **線路**: 桃太郎電鉄風の、白と黒が互い違いの太さ 4 画素の線。横・縦は 4 画素ごと、斜めは (x±y) 8 ごとに替えるので、
  タイルをまたいでも交互につながる。つながる 2 方向の辺(または角)の中点を結ぶ。地面は緑。
- **駅**: 電車の正面のピクトグラム(参照: icooon-mono の「駅」の題材)。黒い円盤に、白い車体・黒い窓・ライト・手前のレール。
- **道路**: 濃い灰の舗装に、黒と白の粒だけ(車線は描かない)。

### 9.4 駅(1 つの駅に 1 マスだけ)

- **位置**: 点だけで登録された駅(ノード)を先に採用し(点どうしは 25 マス以内の重複を間引く)、駅の面
  (駅舎 `building=train_station`、`railway=station`、`public_transport=station`)の重心は、近く(40 マス以内)に駅がなければ使う。
  面は大きい方から。面の重心は敷地の端に寄ることがある(上星川駅では、敷地の重心が駅の点から約 300m ずれていた)ので、点を優先する。
- **面のほかのマス**: 駅舎・`railway=station`・ホーム(`railway=platform`)の面のマスは、線路にする(細線化で 1 本の線にまとまる)。
  `public_transport=station` の面は敷地全体を囲んで大きいので、線路にはせず、位置の決定にだけ使う。
- 駅のマスは、道路・線路より優先して出す。

### 9.5 ROM の動作(`src/main.c`)

- ズームは A でイン、B でアウト(z1〜z18)。起動位置は `data/start.json`(14 章)から `build/start.h` を生成して埋め込む。なければ東京(z10)。
- 通行判定(`probe_run`)は、進む先のマスの VRAM のタイル番号から地形 ID を読み戻して決める。
- Z_MAX = 18。VRAM は 4 画面ミラー(32×30 マスの輪)で、実機では拡張 VRAM を持つカートリッジが要る(エミュレータでは問題ない)。

## 10. 通信(NES ↔ サーバー)

要求は 9 バイト(`server/mapserver.ts` 先頭に詳細)。

| 位置 | 内容 |
| --- | --- |
| [0] | z(1..18) |
| [1:4] | タイル x(24bit ビッグエンディアン) |
| [4:7] | タイル y |
| [7] | xo<<4 \| yo(タイル内のマス位置) |
| [8] | vertical<<7 \| len(1 行または 1 列、1..63 マス) |

応答は len バイト(1 マス 1 バイトの地形 ID)。NES の応答待ちは約 0.35 秒(`src/link.c` の `WAIT_CLOCKS`)で、超えると以後サーバーを使わない
(電源投入直後など、最初の要求が間に合わないとき、リセットが要る)。
サーバーは `--db` で DB を、`--host` / `--port` を指定できる。

## 11. 性能と容量

関東全域(経度 138.4〜140.9、緯度 34.8〜37.1)での実測(Intel Mac、16GB):

| 項目 | 値 |
| --- | --- |
| ブロック数 | 11,956(DB 約 219MB。圧縮前の約 1/10) |
| 駅 | 2,884 個 |
| ビルド時間 | 約 6 分(メモリ圧迫のとき 49〜50 分かかったことがある) |

### 未解決

- **画面の色が化ける**: Mesen で歩くと、同じ地形の絵が、マスごとに違うパレットで表示される。地形 ID とタイルの形は正しい。
  ROM の属性テーブルの計算ロジックは、実座標で再現して期待と一致した。実機の PPU の状態を調べる診断ツール
  (`mesen/dump_ppu.lua`、`server/ppu_dump.ts`、`server/shot_palette.ts`)を用意したが、ダンプ待ちで原因は未特定。
  再発したときの手順・候補・これまでに確認したことは、`doc/memo-palette-glitch.md` にまとめた。地形を作り直した後も起きるかは未確認。
- 実機(Mesen)での表示と、パレット(赤・黄)の色味は、私の環境からは確認できていない(スクリーンショット不可)。

### 制約

- 点だけの駅は、鉄道の `railway=station` / `halt`、`public_transport=station`(`train=yes`)のみ。バス停・地下の出入口は対象外。
- 駅のマスは、面の重心(または点)に置くので、線路の真上にならないことがある。
- 細線化で、複線や操車場は数本の線にまとまる。線路の本数や形は実際より簡略になる(許容)。
- 市街地は建物と同じ(通れない)。高速道路は歩ける。農地は草。
- z10 以下では、一般道路・踏切・駅は出ない。
- 地方別 pbf の境で切れた海岸線は、最後の線分の向きに延ばして閉じる近似。境をまたぐブロックは、後の実行が上書きする。
- 範囲の外に頂点があるだけで範囲を覆う大きな面は取りこぼす(`--margin` で対処)。
- DB 構築のピークメモリは、タイル 1 枚(16×16 ブロック)の作業台とジオメトリで決まる。範囲を広げても増えにくいが、地物の量には比例する。
- 国土地理院の標高タイルは、実行時ではなくビルド時に使う。取得は礼儀として間隔をあけ(既定 50ms)、出典を表示する。

## 15. 付録: 設計判断の記録

- **z18 だけ事前に作る**: 容量と、集約の自由度(しきい値の調整)のため。低ズームのピラミッドは持たず、実行時に集約する。
- **DB に OSM の種別を入れる**: ゲームの地形(ID・絵)を変えても、DB を作り直さなくて済む(絵の変更は ROM とサーバーだけ)。
  ただし、線路の塗り方や駅など、ビルドで決める部分を変えたときは、作り直しが要る。
- **Bun だけで作る**: osmium・GDAL・Python を使わず、Raspberry Pi でも再現できる。GDAL の wasm 版は、数 GB の PBF や
  OSM ドライバの有無が不確実なので採らなかった。
- **海岸線から陸を作る**: 陸地ポリゴン(約 520MB)の取得先に接続できない環境があり、陸地ポリゴンも OSM の海岸線から作られたものなので、同じ結果になる。
- **道路のしきい値を上げた(8.3)**: 都心で、当初の案では道路マスが画面の 60〜99% になり、地図として読めなかった。
- **z10 以下は一般道路を出さない**: 国道が `trunk` で、陸のブロックの約 6 割にあるため、何を基準にしても飽和する。
- **線路は 8 連結の細い線 + 8 方向のタイル + 細線化**: 4 連結で塗ると、斜めの線が階段状になり、曲線がぎざぎざの団子になった。
  線を細く塗り、斜めのタイルでつなぎ、複線を細線化でまとめると、斜めの線が 1 本の斜めの鎖になり、一筆書きになる。
- **駅は 1 マス、点の駅を優先**: 駅の面を線路で塗りつぶすと、団子になった。面の重心は敷地の端に寄るため、位置が正確な点を優先する。
  自宅の駅は、面がなく点だけの登録だった。
- **市街地・農地・高速道路・橋・雪を統合**: 絵と ID を増やさず、ROM の容量(64 種)と見た目の整理のため。
- **パレット**: BG は 4 つしかない。砂を黄色、駅を黒白、建物を赤・黄にするため、山を緑の丘にし、雪をなくした。
- **歩道・横断歩道を除く**: 7.8m のマスでは、車道の隣のマスがすべて交差点になる。
- **座標は 1/64 マスの固定小数点 Int32**: 数百万個の地物のメモリを抑えるため。世界(2^22 マス × 64)が Int32 に収まる。
- **PBF のノードをマージ結合で集める**: ハッシュ表(約 540MB)をやめて、約 150MB に抑えた(関東全域)。
- **Guo–Hall 法の細線化**: Zhang–Suen 法は、幅 2 の斜めの帯を丸ごと消す。
